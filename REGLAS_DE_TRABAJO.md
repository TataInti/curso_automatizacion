# Reglas de trabajo para las próximas clases

## Regla principal

A partir de la próxima clase, cada nuevo encuentro debe prepararse como un **paquete de aula compuesto por dos materiales complementarios**:

1. Un documento principal en formato Markdown (`.md`), que contenga el desarrollo completo de la clase.
2. Una presentación de diapositivas que acompañe la explicación presencial y pueda verse con claridad en el TV del aula.

Las diapositivas no reemplazan al Markdown ni deben ser una copia reducida de todo su texto. El Markdown conserva el detalle; las diapositivas ordenan y hacen visible el recorrido de la clase.

Esta regla se aplica a las clases nuevas. No obliga a rehacer el material existente, salvo que se decida revisarlo.

## Contexto de la capacitación

El curso está orientado a soporte técnico de IT. Los casos deben reflejar tareas como:

- mantenimiento y diagnóstico de hardware;
- tendido y verificación de cables y conexiones de red;
- cámaras y sistemas de seguridad;
- impresoras y periféricos;
- sistemas internos y aplicaciones de uso cotidiano;
- atención de incidentes y situaciones nuevas.

El perfil de los participantes combina experiencia técnica especializada, aprendizaje principalmente práctico y capacidad para resolver problemas sobre la marcha. La formación debe ayudar a conectar esa experiencia puntual con una visión más integral del servicio: personas, equipos, red, sistemas, procedimientos, riesgos y comunicación.

## Criterios para diseñar cada clase

### 1. Partir de una situación de trabajo

Cada clase debe comenzar con un incidente, pedido o tarea reconocible para el equipo. El caso puede involucrar una instalación física, una falla, una consulta de usuario o la necesidad de mejorar un procedimiento.

La actividad debe llevar a los participantes a observar, preguntar, verificar, proponer y comunicar; no solamente a recibir una explicación.

### 2. Conectar el trabajo físico con el razonamiento técnico

Cuando corresponda, la clase debe mostrar el vínculo entre:

- lo que se instala, conecta, mide o revisa físicamente;
- lo que se observa en una red, cámara, impresora o sistema;
- las hipótesis posibles;
- las verificaciones seguras;
- la decisión de resolver, escalar o pedir autorización.

No se debe presentar la parte práctica y la parte conceptual como mundos separados.

### 3. Trabajar en ciclos breves

La secuencia recomendada es:

```text
situación → concepto breve → demostración → práctica → puesta en común → cierre
```

La explicación debe ser breve y servir para mejorar la siguiente acción. Cada clase debe tener un resultado observable y una actividad en la que el grupo pueda mostrarlo.

### 4. Diseñar para un grupo de 12 personas en un espacio pequeño

La propuesta debe contemplar que todos necesitan seguir el mismo TV:

- priorizar parejas o grupos pequeños;
- evitar actividades que requieran que cada persona vea una pantalla diferente al mismo tiempo;
- indicar con claridad cuándo observa todo el grupo y cuándo trabaja cada equipo;
- reservar momentos para que los grupos compartan hallazgos sin extenderse;
- incluir alternativas cuando una demostración física no pueda verse desde todos los lugares.

## Requisitos del documento Markdown

El `.md` de cada clase debe incluir, como mínimo:

- objetivo general y resultados esperados;
- duración y modalidad de trabajo;
- conocimientos o preparación previa necesarios;
- caso o situación inicial;
- explicación conceptual en lenguaje claro;
- demostración y actividad práctica paso a paso;
- preguntas para orientar la observación;
- criterios de seguridad, autorización y escalamiento;
- casos de error o información faltante;
- puesta en común y cierre;
- conexión con la clase siguiente;
- materiales, imágenes o archivos complementarios.

Las instrucciones detalladas, los procedimientos completos, las advertencias y las consignas de evaluación deben permanecer en el Markdown, aunque también se resuman visualmente en las diapositivas.

## Requisitos de las diapositivas

La presentación debe acompañar el mismo recorrido del documento Markdown y estar pensada para una visualización grupal en TV:

- una idea principal por diapositiva;
- títulos breves y visibles desde el fondo del aula;
- poco texto, frases cortas y listas reducidas;
- alto contraste y tamaño de letra legible;
- diagramas, fotografías, capturas o esquemas cuando ayuden a entender;
- pasos numerados para procedimientos y diagnósticos;
- una diapositiva diferenciada para cada consigna importante;
- momentos explícitos para la demostración, la práctica y la puesta en común;
- una diapositiva final con las ideas centrales, los límites y el próximo paso.

No se deben trasladar párrafos extensos del Markdown a las diapositivas. Si una explicación necesita mucho detalle, se presenta oralmente y se deja el desarrollo completo en el documento.

## Seguridad y criterio profesional

Toda clase que incluya soporte técnico debe distinguir claramente entre:

- hechos observados;
- hipótesis;
- verificaciones pendientes;
- acciones permitidas;
- acciones que requieren autorización;
- situaciones que deben escalarse.

No se deben usar credenciales, datos sensibles ni configuraciones reales en los ejemplos publicados. Las demostraciones deben poder repetirse en un entorno controlado y no deben inducir cambios disruptivos sin explicar antes su impacto.

## Paquete de entrega y revisión

Antes de considerar terminada una clase nueva, verificar que:

- el documento Markdown y las diapositivas tienen el mismo objetivo, caso y secuencia;
- los enlaces e imágenes funcionan desde la carpeta de la clase;
- la presentación puede abrirse y verse completa en el TV;
- el texto de las diapositivas se lee sin acercarse a la pantalla;
- las consignas y resultados esperados son observables;
- se contemplan errores, límites, autorización y escalamiento;
- no se incluyeron secretos ni datos reales sensibles;
- el material fue revisado en conjunto antes de la clase.

La clase se considera incompleta si falta el documento Markdown o la presentación que lo acompaña.
